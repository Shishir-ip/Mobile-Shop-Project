Analysis

Security & Limitations

Critical issues examiners commonly ask about - and how to fix them

🔴 Critical

SQL Injection Vulnerability

All SQL queries are built using string concatenation with raw user input (email, password, productId, text fields). Attackers can inject malicious SQL.

Fix: Use SqlCommand.Parameters.AddWithValue("@email", txtEmail.Text) or migrate to Entity Framework Core with LINQ queries.
🔴 Critical

Plain Text Password Storage

User passwords are stored directly in the database without any hashing or salting. Database breach exposes all credentials.

Fix: Hash passwords with bcrypt or Argon2. Use ASP.NET Core Identity or libraries like BCrypt.Net.
🟠 Warning

No Database Transactions

Order placement runs multiple queries sequentially without a transaction. Failure mid-process leaves inconsistent data (order exists but no items, or stock not updated).

Fix: Wrap order insert, item inserts, stock updates, and cart deletion in a SqlTransaction with Commit/Rollback.
🟠 Warning

Stock Race Conditions

Stock decrement uses Stock = Stock - qty without locking. Concurrent checkouts can oversell products.

Fix: Use transactions with proper isolation levels, or check stock availability immediately before decrement with row locking.
🔵 Info

Hardcoded Connection Strings

Connection string Data Source=.\\SQLEXPRESS;... is duplicated across multiple form files. Changes require editing every file.

Fix: Centralize in appsettings.json or project Settings. Use ConfigurationManager to read at runtime.
🔵 Info

Minimal Input Validation

Numeric fields, email format, and required fields lack comprehensive validation. Exceptions may crash the application.

Fix: Add client-side validation, server-side checks, try/catch blocks, and regex patterns for emails and phone numbers.
Viva Prep

Common Questions & Answers

Short, confident responses for likely examiner questions

QHow do users authenticate?
▼

Users register with name, email, phone, and password stored in the Users table with Role='Customer'. Login queries the table by email and password. On success, a static Session class stores UserId, UserName, and Role in memory. If Role is "Admin", the app opens AdminForm instead of the storefront.

QHow is payment handled?
▼

For Cash on Delivery (COD), the app simply records PaymentMethod = 'COD'. For online payments via bKash, the user manually enters their bKash number and transaction ID, which the app stores in Orders.TransactionId. There is no external payment gateway integration - verification is manual/administrative.

QHow do you prevent SQL injection?
▼

Currently the app is vulnerable because queries use string concatenation. The proper fix is to use parameterized queries with SqlCommand.Parameters.AddWithValue("@param", value). Alternatively, using Entity Framework Core with LINQ would eliminate raw SQL entirely and provide built-in protection.

QHow does the app ensure order consistency?
▼

Currently it does not use database transactions. Best practice is to wrap the entire checkout flow - inserting the order, inserting order items, updating stock, and deleting the cart - inside a SqlTransaction. This ensures atomic commit/rollback: either everything succeeds or nothing persists.

QHow are images stored?
▼

Product images are stored as files on disk. The Products.ImagePath column stores the absolute file path (e.g., C:\\Images\\phoneA.jpg). The app loads images from these paths at runtime. If a path is invalid, a gray placeholder background is displayed. Alternatives include storing binary data in the database (VARBINARY) or using cloud blob storage.

QWhat is the role of the Session class?
▼

Session is a static class that acts as an in-memory store for the currently logged-in user's state: UserId, UserName, and Role. It persists only during the application runtime and is lost when the app closes. It enables per-user cart operations and role-based navigation without persistent cookies.
